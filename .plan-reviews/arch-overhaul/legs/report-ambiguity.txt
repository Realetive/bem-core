  # PRD Review (arch-overhaul): Ambiguity                                     
                                                                              
  ## Summary                                                                  
                                                                              
  The PRD's direction is clear, but its key normative terms — "public API",   
  "override-only", "slice done", "quarantine" — are undefined or multiply-    
  defined, and at least three factual anchors are wrong or missing against the
  v5 tree: the v5-base tag does not exist, "pointerevent normalization" does  
  not exist in this codebase, and loader_type_js has no timeout semantics to  
  preserve. The most consequential ambiguity is the public API (open q8): the 
  root export is a side-effect-only barrel, the export map exposes every file 
  via ./*, and the flagship user story US1 imports a named binding that no    
  entry file exports. "Override-only" (G6/CONST-P3) has at least three        
  coexisting mechanical shapes in the repo, and ua — the PRD's own example of 
  a "true override" — has no common ancestor to override. Defining these terms
  in the design doc (glossary + v5-base tag creation + corrected problem      
  statement) is a prerequisite for slice specs to be verifiable.              
                                                                              
  ## Critical Gaps / Questions                                                
                                                                              
  1. **Public API triple-undefined (open q8, US1, C4, G5).**                  
      • Root export ./dist/desktop/bem-core.mjs is built from                 
      build/platforms/desktop.js, which contains only side-effect imports and 
      zero export statements — the dist barrel exports no named bindings today.
      US1's import { BemDom } from 'bem-core' is written against an API shape 
      that does not exist. Creating it would be a "public API addition", which
      Non-Goals forbids. Resolve: does the overhaul create named exports      
      (amending Non-Goals), or is consumption deep-import-only?               
      • package.json "exports": { "./*": "./*" } makes every file in the repo 
      deep-importable. Is a deep import of common.blocks/** public API for    
      CONST-P4 purposes? If yes, the surface can never meaningfully shrink; if
      no, define the boundary. G5's "internal structure invisible to          
      consumers" is unimplementable while the wildcard export map stands.     
      • dist/ is not committed; the "exact inventory" exists only after npm   
      run build. No committed manifest and no export-pinning test exist       
      (test/browser.spec.js runs mocha suites; test/dist checks build         
      artifacts; neither freezes an export surface).                          
      • CONST-P4 names i-bem, i-bem-dom, events as the public API; the PRD    
      treats loader (US6), ua (G2), dom (open q7), and inherit (G4) as public 
      too. Which list governs CONST-P4 policing?                              
      • The package root export points at the desktop build only; is          
      dist/touch/* public? Undefined.                                         
  2. **Parity anchor missing: tag **v5-base** does not exist** (git tag -l is 
  empty; repo has zero tags). Problem statement line 5, US5, C4, and CONST-P5 
  all compare against it. Who creates the tag, at which commit, and when      
  (before slice 1)? Until then "behavior parity by default" (C4) is           
  unverifiable and any done-criterion referencing parity is not machine-      
  checkable, undermining C3.                                                  
  3. **Phantom pointerevent work.** "Pointerevent normalization" appears in   
  the problem statement (i-bem-dom monolith bullet), open q3, and slice 4 —   
  but there are zero pointer/PointerEvent/pointerclick references in          
  production code (grep across common/desktop/touch blocks; hits only in      
  CHANGELOG/MIGRATION history docs). The only jquery __event_type_*           
  redefinition in the repo is desktop.                                        
  blocks/jquery/__event/_type/jquery__event_type_winresize. Either slice 4    
  targets winresize-style event specials (needs rewrite) or it is scoped      
  around work that does not exist. Correct the PRD text before design legs    
  build on it.                                                                
  4. **"Override-only" mechanically undefined, and the PRD's own example      
  contradicts the repo (G6, US3, CONST-P3, slices 1/8).**                     
      • Three coexisting shapes today: (a) base-wrapping function — desktop.  
      blocks/jquery/__config/jquery__config.js exports function(base){ return 
      base }; (b) side-effect redefinition via generated barrel — desktop.    
      blocks/jquery/__event/_type/jquery__event_type_winresize.js mutates $.  
      event.special (mechanism: build/plugins/vite-plugin-bem-levels.js:411-  
      419, same module name from different levels, barrel merge); (c)         
      standalone alternative implementations — desktop.blocks/ua/ua.js (34    
      lines) vs touch.blocks/ua/ua.js (204 lines).                            
      • common.blocks/ua/ contains no ua.js — only templates and __svg. The   
      problem statement calls ua a "true override"; it is actually standalone 
      per-platform logic with no common ancestor. US3's proposed CI rule      
      ("rejects any file in touch.blocks that doesn't correspond to a common. 
      blocks ancestor") would reject both current ua.js files. Define         
      "corresponds to an ancestor" (module defined in common? block directory 
      exists?) before specifying the rule.                                    
      • CONST-P3 "no logic duplication" is unenforceable as stated: desktop   
      and touch ua duplicate nothing, yet both are standalone platform logic. 
      Is "standalone when no common base exists" legal?                       
  5. **jQuery ratchet has a mechanical hole; allowlist=∅ does not imply zero  
  jquery.**                                                                   
      • CONST-P1's check greps *.deps.js for 'jquery' but excludes paths      
      matching (^|/)jquery/. desktop.                                         
      blocks/jquery/__event/_type/jquery__event_type_winresize.deps.js — a    
      real jquery consumer (its .js imports bem:jquery) — is invisible to the 
      ratchet. The 9 allowlist entries and the 9 actual bem:jquery importers  
      are different sets (benchmarks page.deps is counted; winresize is not). 
      • No slice covers desktop.blocks/jquery/* (config + winresize) or       
      common.blocks/jquery/__config. Slice 8 says "jquery wrapper deleted or  
      quarantined" — does that include the desktop redefs? If the wrapper is  
      deleted, does peerDependencies: { jquery: ^4.0.0 } go too? Unspecified. 
      • "Quarantined as an optional compat shim behind a documented escape    
      hatch" (G1) and open q1's bem-core/compat-jquery — "quarantine" and     
      "escape hatch" have no mechanical definition (separate package? export- 
      map subpath? build flag? retained peer dep?). This decides the peer-dep 
      fate and needs a glossary entry.                                        
  6. **Slice "done" is circular (G7, C2, C3, US4).** C3 points at "sdd-check  
  style", but only CONST-P1 (deps grep) and a LICENSE existence check exist as
  machine checks. Behavior-parity slices (4, 5, 7) have no defined            
  verification harness — parity vs v5-base is not machine-checkable without   
  (a) the tag (gap 2) and (b) a specified comparison procedure ("documented   
  per-slice verification" is promised by US5 but never defined). What counts  
  as a "requirement" for the <=12 cap is undefined; "~6-8 slices" hedges while
  the Rough Approach enumerates exactly 8.                                    
  7. **G3 invents semantics.** loader_type_js (62 lines) implements load/error
  callbacks with in-flight dedup — there is no timeout. "Semantics (async     
  script load, error reporting, timeout)" must be corrected to what exists, or
  slice 3's parity bar is unknowable. Similarly US6 promises "keeps working ...
  or follows a documented one-line migration" — which branch is the contract?
