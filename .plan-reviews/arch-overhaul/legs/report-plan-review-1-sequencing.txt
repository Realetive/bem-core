## Summary

The DAG's topology is sound: every stated edge is real (some only via S6's
release-prep role), every correctly-omitted edge was checked and is genuinely
unneeded (S1↛S4, S3↛S4/S5, S1↛S3, S2↛S3), the allowlist arithmetic (9→∅) matches
the CONSTITUTION.md CONST-P1 allowlist 1:1, and the CONST-P6 −3 riding S1 is
achievable inside S1 as scoped. Two must-fix defects sit at the DAG's seams:

1. **The staged final gates auto-activate one slice too early.** The skip-guard is
   "allowlist ≠ ∅", but the allowlist hits ∅ *after S5* while the gates' own
   predicates (no-jquery-in-artifact; "wrapper dirs gone, package.json clean") only
   become true at S6 — and jquery legitimately remains in the payload at S5 (the
   platform entries import `bem:jquery` directly; verified). Auto-activation keyed
   on allowlist-∅ makes S5's merge commit CI-red, re-breaking the exact
   per-slice-green invariant (C2/G7) that prd-align-1 GA-F2 fixed.
2. **Parallel-slice entry-list handling is unscheduled.** The hand-maintained
   platform entries (`build/platforms/{desktop,touch}.js`) import
   `jquery__event_type_winresize` (desktop, deleted S2) and `loader_type_bundle`
   (both, deleted S3) — verified. Generation that would obsolete the lists is
   scheduled only as the ambiguous "S0–S1 tooling", so S2/S3 can land while the
   lists are live → unresolvable `bem:` import → build breaks; and parallel
   hand-edits to the same two files race each other and OQ6's payload-parity
   baseline.

Six should-fix items cover the spurious/omitted "S1 soft" edge, the "(S0/S6)"
plugin-validation ambiguity, three verifier-churn gaps (S1 pin-test update, S6
final budget caps, S3 loader canonical path), and the one-directional ratchet
that lets forgotten allowlist shrinks pass silently until S6.

## Findings

### MUST-FIX

**MF-1. Final-gate auto-activation binds at S5, not S6 — re-breaks C2/G7 (GA-F2 regression).**
Sections: Executive Summary staged-gate bullet ("…**activate at S6**, when the
CONST-P1 allowlist reaches ∅"); Key Components 10 ("**activate at S6** (or
auto-activate once the allowlist reaches ∅)"); Key Components 13 ("until the
allowlist reaches ∅ and is conclusive (binding) at S6").
Slices/edges: S5→S6 boundary; S5's own done-gate.
Why it breaks: Exec Summary states "∅ after S5" — so on S5's merge commit the
guard "short-circuit while the allowlist ≠ ∅" flips off and the final assertions
bind one slice before their own preconditions exist:
- no-jquery-in-artifact: the payload entries import jquery *directly by module*,
  not via deps — `build/platforms/desktop.js:30` `import 'bem:jquery'` (plus
  `:29` `bem:jquery__config`), `touch.js:29–30` (verified @ f2ab61e). Deleting the
  wrapper, `desktop.blocks/jquery/*`, and the peer/dev deps is S6 work; at S5 the
  artifact legitimately contains jquery, so the binding assertion fails.
- CONST-P1 final predicate: conjunctive over S6-only facts ("wrapper dirs gone,
  package.json clean" — package.json still carries `peerDependencies.jquery` +
  `devDependencies.jquery` `^4.0.0`, verified). Cannot pass at S5.
Net: S5 CI red → violates "Every slice leaves `v5` buildable and tests green"
(Design position 6 / C2 / G7) — the exact failure mode prd-align-1 GA-F2 corrected
for S1–S5, reintroduced for the S5→S6 window.
Suggested fix (three cells): guard on the conjunction, not the allowlist alone —
"short-circuit to preview + exit 0 while (allowlist ≠ ∅) **OR** the wrapper block
still exists / package.json still lists jquery; binding otherwise (first possible
binding commit = S6)". Concretely: Exec Summary bullet, KC10 staging paragraph,
KC13 CONST-P1 sentence — replace "auto-activate once the allowlist reaches ∅" with
"auto-activate once the allowlist is ∅ **and** the wrapper block is deleted (no
earlier than S6)". Alternative shape: key the auto-activation on the CONST-P1
final predicate's own remaining-conditions count, so binding and pass-ability
flip on the same commit.

**MF-2. S2/S3 deletions hit the platform entry lists; neither the entry edit nor the generation switchover is scheduled in any slice.**
Sections: Key Components 8 ("Init registry (S0–S1 tooling) — platform entry
modules **generated** from the plugin's scan registry (replacing hand-maintained
ordered import lists)"); Open Question 6 ("the S0/S1 generation REQ"); Slice
series rows S2 ("winresize deleted") and S3 ("`loader_type_bundle` deleted").
Slices/edges: S0→{S1,S2,S3} fan-out; S1∥S2∥S3 parallelism.
Why it breaks (repo-verified): the hand lists reference exactly the entries S2/S3
delete — `build/platforms/desktop.js:31` `import 'bem:jquery__event_type_winresize'`;
`desktop.js:62` and `touch.js:62` `import 'bem:loader_type_bundle'`. If a deletion
slice merges while hand lists are live, Vite cannot resolve the `bem:` specifier →
build fails → the slice cannot go green without entry-list work that appears in
no slice row, no TESTS item, and no Harness Δ. Generation is pinned only to the
two-slice window "S0–S1", so:
- if generation lands S0: no problem (deletions flow through the scan) — but the
  doc doesn't say S0;
- if generation lands S1: S2 and S3 run **in parallel with** the switchover —
  whichever merges first must hand-edit both lists (three-way textual race on the
  same two files), and OQ6's payload-parity assertion "against today's hand
  lists" loses its baseline the moment any parallel slice edits them.
Suggested fix: pin the switchover to S0 — S0's KC8 line becomes "Init registry
(S0): platform entry modules generated from the scan registry; hand-maintained
lists deleted in S0 (payload-parity assertion vs the pre-S0 lists runs in S0)".
Then S2/S3 rows need no entry work (deletions auto-flow through regeneration),
and OQ6's baseline is a fixed, pre-parallel state. If S1 must own generation
instead, then S2 and S3 rows + TESTS must each gain an explicit "entry-list edit
(hand or regenerated) + local payload-parity re-baseline" item and the DAG note
should warn about the shared-file race.

**SF-5. Loader canonical path is inconsistent across three sections — S3's barrel/pin disposition is ambiguous.**
Sections: Key Components 7 ("Loader (`loader/loader.js`, S3)"); Interface "Root
barrel" (`export { default as loader } from 'bem:loader_type_js'`); "Supported
deep-import inventory" ("loader (js)").
Evidence @ f2ab61e: `common.blocks/loader/` contains only `_type/loader_type_js.js`
and `_type/loader_type_bundle.js` — no `loader/loader.js` exists, so KC7 names a
new canonical path while the end-state barrel and pinned inventory keep the old
one. Post-S3 either (a) the implementation stays at `loader_type_js` (KC7's path
is wrong), or (b) `loader/loader.js` is canonical and the barrel + pin inventory
change in S3 — unscheduled (same class as SF-3), and the end-state barrel would
then import through the *deprecated* one-release re-export, breaking when the
re-export dies.
Suggested fix: pick one canonical path. If `loader/loader.js`: Interface barrel
becomes `from 'bem:loader'`, deep-import inventory gains it, the deprecated
re-export is the old `loader_type_js` path, and S3's row/TESTS gain "barrel +
pin-inventory switch". If the old path stays canonical: correct KC7 to
`loader/_type/loader_type_js.js` and note the file is rewritten in place.

**SF-6. The CONST-P1 ratchet only catches additions — a forgotten shrink passes silently until S6.**
Sections: Key Components 10 ("per-slice binding from S0 = gz-byte caps + the
CONST-P1 allowlist ratchet + CONST-P6 baseline ratchet"); Key Components 13
(CONST-P1 final predicate); CONSTITUTION.md CONST-P1 sdd-check (repo evidence:
`comm -23` JQ ALLOW — set difference only in the additions direction).
Why it matters: "Ratchet diffs across the series ARE the machine-readable
migration history" (Data Model 5) — a slice that migrates a consumer but forgets
the allowlist edit stays green through S1–S5 (stale entries are invisible), and
the error surfaces only at S6's binding predicate, where attribution is lost.
Same asymmetry applies to the CONST-P6 baseline ratchet.
Suggested fix: S0's gate upgrade adds the reverse difference — fail when
ALLOW−JQ ≠ ∅ (allowlist entry whose file no longer consumes) — or, more simply,
each slice's done-gate grep predicate pins the exact expected allowlist/baseline
contents after its Δ. One clause in KC13 (or KC10's staging paragraph) suffices.
