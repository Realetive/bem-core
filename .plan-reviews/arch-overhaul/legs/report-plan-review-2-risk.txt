# Plan-review-2 · risk — arch-overhaul (S0–S6 slice plan)

## Summary

The plan's risk posture is strong where it has already been stress-tested (S4×S5 interim
interop, override-barrel TypeErrors, staged final gates, bench noise, doc rot): every one of
those carries a named mitigation with an owning slice and a verifier. This round's findings
concentrate where the existing Risks table does not reach: (1) an unscheduled hard dependency

## Findings

### F1 [must-fix] — S6's jquery removal has an unscheduled prerequisite: the test harness is a jquery consumer no slice owns

Anchor: Slice series → S6 row ("jquery dev+peer deps gone … npm ci green") + Key Components 13
("final multi-grep predicate (deps manifests ∅, sources+harness ∅, wrapper dirs gone,
package.json clean)") + Implementation Plan TESTS item 4 (Harness Δ).

The harness imports jquery in three places the allowlist cannot see (CONST-P1 greps only
`*.deps.js`): entry.js's direct `import $ from 'jquery'` + shim-map entry `jquery: $`, and
vite.test.config's `optimizeDeps.include: ['jquery']`. All 25 spec files are ym-authored; 4
still require jquery through the shim — the same four corpora the plan cites as pinned-green
through S5. KC 12's block-by-block conversion is never *required*, so a slice can keep its
corpus ym-authored and green via the shim, leaving `jquery: $` alive past S5. The only
detector is the final predicate's "sources+harness ∅" conjunct, which first binds at S6's own
deletion commit — the discovery lands mid-S6, in the series' fattest slice.

Suggested edit: S5 outcome cell + TESTS item 4 gain an explicit carrier — "harness exits
jquery in S5: `__events_type_bem.spec.js` + `i-bem-dom.spec.js` converted to ESM (or
re-authored against the S5 registry) AND the shim-map `jquery` entry, entry.js
`import $ from 'jquery'`, and the vite.test.config optimizeDeps jquery line deleted in the
same commit"; S2/S4 Harness Δ cells carry the analogous conversions (dom.spec.js /
__events_type_dom.spec.js); S6 done-gate grep set gains "zero `jquery` imports repo-wide
(sources, harness, configs)" so the final conjunct cannot surprise.
Slices: S2, S4, S5, S6.

### F2 [must-fix] — S0's entry-generation bet names the what, not the how (artifact, ordering, drift)

Anchor: Key Components 8 ("platform entry modules **generated from the plugin's scan
registry**; the hand-maintained lists … deleted in the same S0 commit, with the
payload-parity assertion") + Slice series → S0 outcome cell.

Three load-bearing details unspecified:
1. Artifact form: vite.config consumes `build/platforms/${platform}.js` as lib.entry. After
   the hand lists die, is the generated entry committed (lockfile-style — needs a freshness
   check) or generated at build time (needs a prebuild step; parity assertion becomes a
   build-time check)? Each answer changes the S0 REQ shape.
2. Ordering: the scan registry is a Map built in readdirSync order (nondeterministic across
   platforms). Set-parity is sufficient only because every cross-module dependency is a
   static `bem:` import (verified @ f2ab61e: winresize, __init_auto, __events_type_dom all
   import their deps) — the transitive ESM graph, not list order, carries evaluation order.
   That argument is true today and written nowhere; a future side-effect module without a
   static edge (the jquery__config-before-jquery pattern) would silently depend on emitted
   order.
3. Drift: if committed, CI must regenerate + diff, or the file rots exactly like the hand
   lists D-8 cites as the motivation for generation.

Suggested edit: KC 8 + S0 outcome cell gain one sentence each: "generation output committed
at build/platforms/*.gen.js; imports emitted in canonical sorted order — sound because
cross-module ordering is carried by static bem: import edges (verified); CI re-runs the
generator and diffs (freshness); payload-parity assertion compares the emitted set against
the checked-in pre-S0 baseline."
Slices: S0 (mechanism); S2/S3 (deletions flow through it).

### F3 [should-fix] — Loader semantics table omits the cross-origin/CORS break

Anchor: Interface → Loader surface, semantics table + "Documented semantic shift: **ES
modules only** — classic scripts defining globals no longer execute."

Classic script injection loads cross-origin URLs with no CORS; dynamic import() requires CORS
headers on the target. A consumer loading any third-party URL breaks at runtime with a
network error even if the target is a valid ES module. The audit is the right mitigation but
its checklist is undefined while the table — the design's canonical enumeration of semantic
deltas — misses the row.

Suggested edit: semantics table gains `| cross-origin script URLs (no CORS needed today) |
behavior change — import() requires CORS on the target; S3 audit must confirm zero
cross-origin loader URLs |`; S3 MIGRATION cell gains the line.
Slices: S3.

### F8 [should-fix] — Revert protocol is implicit: non-tip single-slice reverts redden CI without a wedge, and nobody wrote that down

Anchor: Design positions 6 + KC 10 (two-directional ratchets) + Risks and Mitigations table.

Walking each slice's revert story: ledgers/ratchets/budgets ride slice commits (revert
restores both sides — consistent); staged gates re-key off git-tracked state (allowlist ≠ ∅
after a revert → skip/preview mode; the round-1 re-keying is sound under revert); hand lists
and all S0-generated artifacts are recoverable from git history — no one-way doors, no
wedge. The residual hazard: reverting a non-tip slice whose outputs a landed successor
consumes — concretely S2 (S4's engine builds on S2's facade) and S5 (S6's deletions assume
S5's registry/init) — restores code that no longer links against the successor's rewrite;
CI reddens at build/test, not at any gate, which an operator can misread as a gate bug.

Suggested edit: Risks table gains a row: "Mid-series revert of a non-tip slice (S2/S5) vs
landed successors | Medium | Reverts are stack reverts — reverting slice N with N+1 landed
requires reverting N..M; gates self-consistent (skip-mode rebinds), red comes from code, not
gates"; mirrored as a one-line revert note in the Implementation Plan. Slices: cross-cutting.

### F9 [should-fix, spike] — One timeboxed spike retires the S3 bundler unknown now

Anchor: Slice series → S3 row ("`import()`-based loader") + Key Components 8/9.

The plan has exactly one external-runtime bet nobody has exercised: dynamic
`import(variableUrl)` through Vite 8 / rolldown in both contexts that matter — the dev-server
test harness (bundled, jquery-inlined) and the lib build. Rolldown's import analysis of
non-analyzable specifiers can warn or error depending on config; if it errors, S3 needs a
carve-out (`@vite-ignore` or equivalent) discovered mid-slice. A timeboxed S0-carried spike
(one module importing a variable URL through both configs) converts unknown to documented
behavior before S3 starts, and doubles as an early smoke test that generated entries survive
both build paths.

Suggested edit: S0 outcome cell gains "spike REQ (timeboxed): dynamic import(variable)
through vite.test.config dev server + lib build; record rolldown behavior" (or a standalone
investigation bead pre-S3). Slices: S0, S3.

### F10 [should-fix] — Sizing: S3 and S6 carry hidden REQ mass (F1 lands in S6 by default)

Anchor: Slice series table, REQ est column (S3 "4–6", S6 "8–10").

S3's 4–6 excludes harness-side work its closure predicates imply (loader specs need servable
ES-module URLs; the 33-line loader_type_js.spec.js corpus must grow promise-rejection +
once-warn re-export suites). S6 is the series' fattest slice (deletion + enforcement +
release prep + bounded README + docs pass + budget final caps + UMD drop + dev/peer removal +
notices grep + MIGRATION/CHANGELOG consolidation) and by default also inherits F1's harness
exit. Both are at over-cap risk with C2's ≤12 discipline as the only brake — mid-flight
splits cost more than pre-authorized ones.

Suggested edit: adopt F1 (moves the harness exit to S5); S3 TESTS enumeration gains
"ES-module URL fixtures for loader specs" (floor nudges to 5–6); pre-authorize an S6 split
(S6a deletion + enforcement + final gates; S6b release prep + docs/README + ledger
consolidation) in the Implementation Plan, mirroring F7's S0 language. Slices: S3, S5, S6.
