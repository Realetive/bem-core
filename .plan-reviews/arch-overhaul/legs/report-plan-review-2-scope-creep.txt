## Summary

The plan is scope-tight for a strangler series with binding machine-check demands
(C1/C3/G6/US3): **0 must-cut, 6 should-cut, 1 defer**, plus ~30 explicit acquittals.
The over-engineering lens produced **zero cut findings** — every machinery candidate
(CONST-P6 baseline, bundle gate, TESTS contract, MIGRATION ledger, skip/preview staging,
shim-map ratchet, plugin hard error, WeakMap, decomposition granularity) traces to a
binding requirement (G6/US3, C3/CONST-P1, G7/CONST-P4, Q6, C4) or replaces a
known-defective existing mechanism (the >400 magic floor). The genuine creep is
concentrated in S0 (at-cap) and S3 (smallest slice): a deps-manifest lint no requirement
carries; a dead-code cleanup scheduled as a named outcome; a stale "Node floor pinned"
phrase contradicting the already-applied NG-F7 cut; and a one-release compat bridge that
contradicts the hard-fork delete-outright culture (D-1) while CONST-P4/US6 are satisfiable
with a MIGRATION line. Two smaller items: the B6 startup bench scenario (redundant with
the bundle byte gate + B1) and two unspecified-polish mentions (scope explicit-throw,
_buildModValRE memoization). All plan-native deferrals (inherit, absolute budgets,
tree-shaking, content redesign, keyboard convoy) verified NOT load-bearing for any slice.
Net REQ effect: S0 11–12 → ~10–11 (cap pressure relieved), S3 4–6 → ~4–5; no slice grows.

## Findings

### SC-1 [should-cut] `.deps.js` schema+resolution lint (S0)
- Anchor: Slice table S0 row — "`.deps.js` schema+resolution lint + entity-converter
  unification"; Data Model 1 — "`.deps.js` stays a **documented manifest, never a build
  input** — schema+resolution lint added".
- Slices: S0.
- PRD decision: no requirement carries a checker over a manifest the design itself
  excludes from the build (D-9). PRD Non-Goals ("No bundler/CI changes beyond what
  architectural slices require"); the manifest's only load-bearing role — CONST-P1
  ratchet substrate (Data Model 5) — is already consumed by the existing grep. The lint
  guards a doc artifact with zero in-repo mechanical consumers (hard fork, single
  consumer, Q2).
- Suggested edit: delete the lint clause from the S0 cell and Data Model 1; D-9 keeps
  "documented manifest, never a build input" as prose. Manifest hygiene, if wanted, is
  one sentence in S6 release prep — not a fence-slice REQ.

### SC-2 [defer] entity-converter unification (S0 → S6 ride-along)
- Anchor: same S0 cell + Data Model 1 — "the two divergent entity-converters unified
  (dead `bemEntityToModuleName` removed)".
- Slices: S0 → S6.
- Repo-verified: `bemEntityToModuleName` is defined and exported only
  (`build/plugins/vite-plugin-bem-levels.js:280` def, `:669` export); zero production
  call sites. "Unification" = deleting dead plugin-internal code.
- PRD decision: no requirement names it; dead-code removal is release-prep hygiene, not
  fence-slice scope. S0 is at-cap (11–12) and nothing downstream depends on it — doing
  it early buys nothing.
- Suggested edit: S0 cell drops the phrase; S6 outcome cell gains "dead plugin-internal
  `bemEntityToModuleName` deleted (ride-along)" — or fold into S0's plugin-validation REQ
  as incidental cleanup if S0 has slack after SC-1/SC-3.

### SC-3 [should-cut] stale "Node floor pinned" in S0 outcome (doc fix)
- Anchor: Slice table S0 row — "Node floor pinned"; contradicts the CI wiring section —
  "Node matrix unchanged — the existing [20] entry already pins the ≥20 floor (current
  matrix [20,22])". prd-align-2 NG-F7 already cut the matrix change; package.json
  engines ≥20 verified @ f2ab61e.
- Slices: S0.
- PRD decision: NG-F7 (applied): "Node matrix realignment [20,24] required by no slice".
  The S0 phrase is a pre-NG-F7 leftover; as written it schedules a no-op or an
  already-cut change.
- Suggested edit: delete "Node floor pinned" from the S0 cell (the CI-wiring sentence
  already records the no-change position).

### SC-4 [should-cut] loader deprecated re-export bridge (S3)
- Anchor: KC 7 — "the old mod path becomes the one-release deprecated re-export
  (once-warn; callable shape preserved)"; S3 row closure predicate "deprecated re-export
  present with once-warn"; TESTS S3 "deprecated deep-import re-export once-warn";
  deep-import inventory "the `loader_type_js` mod path rides as the deprecated
  one-release re-export".
- Slices: S3.
- PRD decision: US6 is satisfied by the "or" branch ("follows a documented one-line
  migration to `import()`"); CONST-P4 allows shrink "inside a slice whose spec documents
  the migration" — a MIGRATION line, not a bridge; Q2/D-1 set the hard-fork
  delete-outright culture for compat surfaces. In-repo consumers verified: only the
  platform hand lists + spec harness reference the old path (switched mechanically at
  S3); the bridge serves hypothetical external deep-importers — the population Q2
  declares empty.
- Cost: bridge + once-warn machinery + a dedicated once-warn test inside the series'
  smallest slice (4–6 REQ).
- Suggested edit: delete the old mod path outright with a bilingual MIGRATION entry
  naming old/new paths (callable form preserved by the new root module; promise return
  additive — already in the Loader surface); closure predicate becomes "zero
  `loader_type_js` references repo-wide (barrel, generated entries, harness entry.js
  switched; spec converted)"; drop the once-warn test item. This is a variant of
  SQ-SF-5's option (a) (canonical switch kept, bridge dropped), not a rollback.
- Counterweight (why medium confidence): upstream/CONST-P4 MIGRATION culture tolerates
  one-release bridges, and the coordinator preferred bridge-adjacent option (a) in
  round 1. If bridge culture is weighed heavier, keep — but then it is a deliberate
  compat affordance, not a requirement.

### SC-5 [should-cut] bench scenario B6 "startup" (S2)
- Anchor: KC 11 — "six scenarios B1–B6 (init throughput, delegated dispatch, BEM emit,
  live-collection, destruct no-leak via heap delta, startup)"; S2 row "bench project
  B1–B6"; TESTS S2 "bench B1–B6".
- Slices: S2.
- PRD decision: Q6 anchors the harness as "the perf harness for the later i-bem-dom
  rework" (= S4/S5). B1–B5 each measure a path a slice changes (B2→S4 engine + WeakMap
  risk row; B3→S5 registry; B4→collection/WeakMap; B5→D-5 leak-by-construction, its only
  verifier). B6 startup measures payload bytes + init — both already gated (bundle byte
  caps; B1).
- Suggested edit: five scenarios B1–B5 in KC 11, the S2 row, and TESTS S2. (If S6 wants
  a startup smoke number, it can ride the final bench run — not a scenario.)

### SC-6 [should-cut] `bemDom.scope/doc/win` "explicit throw" polish (unrequested behavior tightening)
- Anchor: Interface → DOM type contract — "lazy getters (`body`/`document`/`window`),
  never null; explicit throw if body genuinely absent (replaces silent-null footgun)".
- Slices: S4 (scope anchor decision, OQ-3) / S5 (decomposition makes them lazy).
- Repo-verified today: `bemDom.scope = $('body')` at module eval (`i-bem-dom.js:1215`;
  `scope : null` default `:938`) — silent empty on missing body.
- PRD decision: C4 "behavior parity by default … unless a slice's spec documents a
  migration". The throw is an observable change on an edge path that no requirement
  demands (US1 "nothing regresses"; no user story reads scope-before-body). As written
  it is polish plus an undocumented break.
- Suggested edit: either (preferred) drop the throw clause (lazy getter preserves
  today's empty-body behavior), or keep the throw AND enumerate it in the owning
  slice's MIGRATION cell as a C4 break. Do not leave it as silent polish.

### SC-7 [should-cut] `_buildModValRE` memoization mention (S5)
- Anchor: KC 6 — "`_buildModValRE` memoized".
- Slices: S5 (decomposition).
- Repo-verified: `i-bem-dom.js:850` builds `new RegExp` per call today; no bench
  scenario measures mod matching (B1–B6 don't).
- PRD decision: no requirement; premature-optimization class — a perf mechanism with no
  requirement anchor and no scheduled evidence.
- Suggested edit: delete the phrase from KC 6; leave memoization to S5 implementation
  latitude if the rewrite touches the call sites anyway. Near-zero stakes either way.
