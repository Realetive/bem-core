NOTES

  # PRD review (arch-overhaul): stakeholders                                  
                                                                              
  ## Summary                                                                  
                                                                              
  The PRD's stakeholder model is internal-facing. Its six user stories        
  (US1–US6) cover the modern-stack consumer, internal frozen-consumer         
  maintainers, platform contributors, slicing engineers, the                  
  architect/reviewer, and the legacy loader user — but the repo evidence shows
  several constituencies that the slice plan will hit without anyone named to 
  answer for them:                                                            
                                                                              
  1. **External library consumers of the jquery wrapper and peer-dep          
  contract** — package.json declares peerDependencies: jquery ^4.0.0; README. 
  md ("jQuery 4 is a peer dependency — install it alongside") and common.     
  blocks/jquery/jquery.en.md/.ru.md document the jquery block as a public     
  block; the dist build externalizes jquery for both ESM and UMD (build/vite. 
  config.js: external: ['jquery'], globals: { jquery: 'jQuery' }). The wrapper
  is importable through the package exports ./* wildcard. OQ1 (delete vs      
  compat shim) is the PRD's only nod to them, and no user story exists.       
  2. **Touch-platform consumers** — exports["."] points only at .             
  /dist/desktop/bem-core.mjs; the touch build (dist/touch/) has no exports-map
  entry. Browser tests run Chromium-only headless (playwright.config.js:      
  browserName: 'chromium'), so the platform most affected by ua → env (slice  
  1) has the thinnest verification.                                           
  3. **Spec/test-harness maintainers** — ~25–28 block spec files run through a
  hand-rolled legacy shim (test/browser/entry.js modules shim, mocha-in-page);
  node tests cover only build/plugins and i18n (package.json test script). C3 
  demands machine-checkable done-criteria, but no slice role owns harness     
  evolution. Additionally test/dist/build-fixtures.js still requires ENB-era  
  packages removed in v5 (bem-walk, borschik, libs/bem-pr) — dead tooling that
  will confuse slice engineers.                                               
  4. **Benchmark keepers** — i-bem-dom.tests/benchmarks.blocks (b1, b2, page; 
  page.deps.js depends on jquery). OQ9 flirts with deleting them exactly when 
  slice 7 (i-bem-dom decomposition) needs perf evidence most; C4 enforces     
  *behavioral* parity only, perf parity is unowned.                           
  5. **Docs readers (ru/en)** — the repo is systematically bilingual:         
  README/README.ru.md, MIGRATION/MIGRATION.ru.md, CHANGELOG/.ru,              
  CONTRIBUTING/.ru, per-block *.en.md/*.ru.md (jquery, loader, ua all         
  documented in both languages), plus common.docs/ site content and JSDoc. G7 
  names only "MIGRATION.md"; the ru twin and the block docs (e.g. loader.en.md
  documents loader_type_bundle as public API; ua.en.md documents the sniffed  
  fields) are unmentioned, so ru docs will rot silently.                      
  6. **The fork's release/versioning owner** — the overhaul ships public-API  
  shrinkage (CONST-P4) and a possible peer-dep removal, i.e. semver-breaking  
  changes, but the PRD contains no versioning strategy (5.x vs 6.0), no       
  deprecation-notice channel, and package.json still points repository.url at 
  upstream bem/bem-core. Who cuts releases and who publishes is unassigned.   
  7. **The reviewer's anchor is missing** — CONST-P5 and US5 anchor           
  before/after comparison at tag v5-base, but git tag is **empty** in the repo.
  Every slice's parity verification (C4) currently has no comparison point.   
                                                                              
  The single most important structural fact: the fork's contributor base is   
  effectively one human (Realetive) plus agent commits (git log: 41 upstream- 
  import commits by veged, 8 by Claude, 1 by Realetive). A per-slice sign-off 
  matrix is therefore not a bureaucracy question — it must explicitly         
  acknowledge which "approvers" are the same person, and what agent review may
  approve autonomously vs. what requires the human owner.                     
                                                                              
  ## Critical Gaps / Questions                                                
                                                                              
  1. **No **v5-base** tag exists.** US5 and C4 both assume diffing against v5-
  base; git tag returns nothing. Slice 0 (or the PRD itself) must require     
  creating the tag at the current main HEAD before slice 1 lands, else every  
  "behavior parity vs v5-base" done-criterion is unverifiable. Owner: fork    
  owner. *Blocking for slice 1.*                                              
  2. **OQ1 (jquery escape hatch) has no owner, no evidence base, and no user  
  story.** Repo facts that constrain it: peer dep jquery ^4 is documented in  
  README (en+ru); the wrapper is a README-listed public block with bilingual  
  docs; dist externalizes jquery (ESM import + UMD global jQuery); the ./*    
  exports wildcard makes bem-core/common.blocks/jquery/jquery.js a resolvable 
  import path today. Deciding "delete outright" at slice 8 without a consumer 
  census (even a grep across the fork's own downstream repos) is a gamble;    
  deciding "compat shim" late forces re-planning of slices 2–5 (interim code  
  chooses native APIs vs continued $ usage). The PRD should (a) add a US for  
  the wrapper-consuming external app, (b) schedule the consumer census +      
  decision milestone before slice 2's spec is written, and (c) tie the peer-  
  dep removal to a version decision (see gap 6).                              
  3. **No sign-off matrix.** The PRD never says who approves each slice.      
  Proposed matrix (see Important Considerations) should be added to the design
  doc; in fork reality most roles collapse to the fork owner, which should be 
  stated so agents know when to escalate to the human.                        
  4. **Perf-parity ownership for slice 7 conflicts with OQ9.** If benchmarks  
  are deleted as a "pre-Vite relic", the decomposition slice loses its only   
  measurement harness and C4 will not catch live-collection perf regressions. 
  The stakeholder question "who attests no perf regression?" is currently     
  unanswerable. Recommendation: benchmarks survive (migrated off jquery in    
  slice 2 as planned) through slice 7; deletion decided only afterwards.      
  5. **Touch verification gap.** touch.blocks/ua/__dom/ua__dom.js reads ua.   
  ios/android/opera/wp/bada/chrome/svg/landscape/width/height/screenSize —    
  legacy-platform UA forks. Slice 1 replaces the substrate these read from,   
  yet Playwright coverage is desktop-chromium-only. Slice 1's done-criteria   
  need either touch-device emulation in CI or a named touch-domain owner who  
  signs off the env API shape and the preserved legitimate UA branches (iOS   
  Safari gesture quirks are the classic case capability detection cannot      
  answer).                                                                    
  6. **Versioning and publishing unowned.** Public API shrinkage (CONST-P4) + 
  possible peer-dep removal = major-version bump under semver; the PRD is     
  silent. Intermediate slices published with jquery still external but wrapper
  half-quarantined create confusing intermediate package states. Also         
  repository.url still points to git://github.com/bem/bem-core.git —          
  publishing provenance belongs to whoever owns the release role.             
  7. pointerclick** and friends are an implicit public contract with nobody   
  attesting.** desktop.blocks/jquery/__event/_type/* special events           
  (pointerclick, winresize…) are part of the observable event surface external
  app code can bind (and MIGRATION.md culture treats jquery redefinitions as  
  user-facing). Slices 4–5 must preserve event-name behavior (_domEvents().   
  on('pointerclick')); the PRD's OQ3 asks *where* normalization lives but not 
  *who guarantees the contract* — needs a named attester in those slices'     
  done-criteria.                                                              
  8. loader_type_bundle** is documented public API.** loader.en.md/.ru.md     
  document type bundle with signature; G3's "removed with a documented        
  migration" is right, but the docs pair must be updated in the same slice and
  the ru twin explicitly listed (docs-reader stakeholder).

  **Conflicting needs to surface, not bury:**                                 
                                                                              
  • *Clean break vs compat escape hatch* — internal desire to delete 30+ kB vs.
  external contract (peer dep, README docs, ./* import path, UMD global).     
  These pull slices 2–8 in opposite directions until OQ1 is decided; decide   
  early.                                                                      
  • *Benchmark deletion (OQ9) vs perf evidence for slice 7* — as above;       
  sequencing conflict.                                                        
  • *CONST-P3 enforcement lint vs platform contributors* — a lint that rejects
  any touch.blocks/desktop.blocks file without a common ancestor (US3) is     
  ergonomic only with good error messages and a documented "where does shared 
  behaviour go" rule; too strict and it fights the override culture, too loose
  and G6 fails. The lint is repo-local tooling today; if it ever ships in     
  build/plugins/* (which IS exported via ./build/plugins/*), it becomes public
  API with its own stakeholders.                                              
  • *Bilingual doc parity vs slice velocity* — 6–8 slices × (MIGRATION.md +   
  MIGRATION.ru.md + README + README.ru.md + affected block docs ru/en +       
  CHANGELOG pair) is real, unestimated work; if unassigned, ru docs rot (the  
  historical failure mode of this repo family).                               
  • *Hand-maintained platform barrels* — build/platforms/desktop.js/touch.js  
  enumerate every block import by hand; every slice that adds (env module),   
  quarantines (compat-jquery), or removes (wrapper, maybe loader_type_bundle) 
  blocks must edit both barrels. The build/plugin maintainer is a quiet       
  stakeholder in all eight slices.                                            
                                                                              
  **Stakeholders the PRD already covers adequately:** US1 (modern consumer),  
  US2 (frozen-consumer maintainers), US3 (platform contributors), US4 (slicing
  engineers), US5 (architect/reviewer — except the missing tag anchor), US6   
  (legacy loader users).
