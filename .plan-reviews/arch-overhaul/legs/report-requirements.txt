  # PRD Review (arch-overhaul): Requirements Leg                              
                                                                              
  ## Summary                                                                  
                                                                              
  The PRD's goals are directionally sound and well-grounded in the repo's     
  actual jquery ratchet (the 9 allowlist entries match grep -rl 'jquery' --   
  include='*.deps.js' exactly), but as *requirements* they are not yet        
  acceptance-testable in the C3 sense ("machine-checkable done-criteria"):    
  most goals describe outcomes ("decomposed", "override-only in practice",    
  "decision documented") without defining the checks that prove them. Two     
  factual grounding errors — the missing v5-base tag and nonexistent          
  "pointerevent normalization" code — undermine US5/C4 and Rough Approach     
  slice 4 respectively. Three user stories (US1, US3, US5) are not end-to-end 
  verifiable as written because artifacts they presuppose (a tagged base, a   
  layer lint rule, bundle-content assertions, an export-inventory test) do not
  exist and are not required by any goal. All grounding below verified by     
  direct inspection of /Users/ryganin/gc/bem-core/bem-core (branch v5, rev    
  f2ab61e).                                                                   
                                                                              
  ## Critical Gaps / Questions                                                
                                                                              
  1. v5-base** tag does not exist (US5, C4, CONST-P5 unanchored).** git tag --
  list returns empty. The PRD's parity strategy (Problem Statement, US5, C4:  
  "diff behavior before/after against tag v5-base") has no comparison point,  
  and no goal requires creating the tag. Add a slice-0 prerequisite ("create  
  annotated tag v5-base at the pre-overhaul commit; record SHA in the design  
  doc") or every parity requirement is unverifiable. This is the single       
  blocking gap: G7 "each slice shippable" and C4 "behavior parity by default" 
  both lean on the anchor.                                                    
  2. **"Pointerevent normalization" is not in the codebase (Problem Statement 
  bullet 5, G5, OQ3, Rough Approach slice 4).** Case-insensitive search finds 
  zero pointer references in production blocks (common/desktop/touch). The    
  only jquery __event_type_* redefinition in the fork is desktop.             
  blocks/jquery/__event/_type/jquery__event_type_winresize.js ($.event.       
  special.resize.preDispatch). No pointerclick/pointernative module exists —  
  MIGRATION.md:48 references common.                                          
  blocks/jquery/__event/_type/jquery__event_type_pointerclick.js, a path that 
  does not exist. Consequences: G5's decomposition inventory lists a          
  nonexistent concern; slice 4 is ~1 file of work, not a slice; OQ3           
  presupposes false facts. Re-ground requirements on a mechanical inventory of
  what i-bem-dom.js (1220 lines) actually contains: live collection/ranges,   
  __events delegation, init lifecycle, DOM api surface — those are real.      
  3. **G1 "zero internal jQuery" is under-specified: which consumers count?** 
  CONST-P1's sdd-check greps only *.deps.js, but jquery usage exists outside  
  that net: test/browser/entry.js:42 does import $ from 'jquery' (plus        
  bem:jquery__config), the modules shim maps jquery: $, and desktop.          
  blocks/jquery/__config plus winresize use $.event. As written, "allowlist   
  reaches zero" can pass while entry.js still imports jquery — acceptance     
  green, goal unmet (US1's "no jQuery in my bundle" false for the test bundle).
  Define the completion predicate: (a) CONST-P1 with ALLOW="" passes AND (b)  
  no bem:jquery/from 'jquery' imports outside the compat shim (or anywhere)   
  AND (c) the browser test harness runs without the npm jquery peer.          
  4. **US1 has no acceptance path: nothing requires bundle-content tests.** No
  test asserts dist bundle contents (the Playwright suite runs the source-    
  level vite test config, not dist), and no goal requires creating one.       
  Suggested: CI check that dist/desktop/bem-core.mjs contains no jQuery       
  signature (or a size budget vs the v5-base dist) + existing suite green.    
  "Nothing regresses vs v5-base" also collides with gap #1.                   
  5. **US3 is internally contradictory today.** "CI rejects any file in touch.
  blocks that doesn't correspond to a common.blocks ancestor" — but touch.    
  blocks/ua/ua.js and desktop.blocks/ua/ua.js have no common ancestor: common.
  blocks/ua contains only templates (ua.bemhtml.js, ua.bh.js), docs, and __svg;
  there is no common ua.js. The strict rule rejects the current tree. G6/US3  
  must either be sequenced after slice 1 (env/ua collapse into common) with a 
  transitional allowlist, or weakened; the PRD never states this dependency.  
  6. **G6's checker is required but unspecified.** "Boundary is checked       
  (lint/rule)" — no such rule exists (eslint.config.js has no layer rules). A 
  goal mandating a new enforcement mechanism should carry its own acceptance: 
  rule exists, wired into npm run lint/CI, demonstrably rejects a synthetic   
  offending fixture, zero violations on the real tree at merge. Otherwise G6  
  completion is prose-review-judged, violating C3's spirit.                   
  7. **OQ8 (public API inventory) is a prerequisite, not an open question.**  
  The exports map (. → ./dist/desktop/bem-core.mjs + a ./* wildcard) is the   
  CONST-P4 enforcement surface and nothing pins it — no API contract tests    
  exist. G5's "public surface pinned by API tests" (slice 7) needs an         
  inventory produced *before* slices 4–6 touch i-bem-dom. Promote "produce and
  test-pin the v5-base public export inventory" to an explicit early-slice    
  requirement.

  ## Observations                                                             
                                                                              
  • Facts that check out: 9 jquery .deps.js consumers match the allowlist     
  exactly (sdd-check grep reproduced); i-bem-dom.js = 1220 lines; inherit.    
  vanilla.js = 121 lines; dom.js = 111 lines; engines node >=20; eslint ^10 / 
  vite ^8; exports "." → dist/desktop/bem-core.mjs (OQ8 premise correct);     
  benchmarks.blocks exists (b1, b2, page).                                    
  • jQuery is a **peerDependency** (^4.0.0 per MIGRATION.md:54), dependencies 
  is empty — US1's accounting should treat it as a peer.                      
  • touch.blocks/ua/ua.js imports bem:jquery at line 7: slice 1 (env/ua) and  
  slice 2+ (jquery) are coupled through this file; slice 1 cannot *finish* ua 
  while touch ua needs jquery. Ordering is right but the coupling should be   
  explicit — design legs should check whether slice 1 delivers a jquery-free  
  touch ua or the file splits across slices.                                  
  • loader_type_bundle.js has zero imports; its only in-repo consumers are    
  build/platforms/desktop.js and tests — OQ6 is answerable now: in-repo no;   
  external unknown (needs MIGRATION.md notice if deleted).                    
  • The ua fork is two different migrations: desktop ua.js is 34 lines of     
  jQuery-1.8-era browser sniffing ({chrome|webkit|opera|msie|mozilla,         
  version}); touch ua.js is 204 lines already doing feature detection (video, 
  svg, connection). Acceptance criteria should treat them separately.         
  • specs/ exists but is empty — US4's "machine-checkable done-criteria" has a
  home but no spec-format convention yet; the design doc must define it (C3   
  gestures, never requires).                                                  
  • MIGRATION.md already carries jquery peer-dep and removed-method guidance —
  slice specs can reference rather than rewrite.
